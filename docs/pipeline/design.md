# Tool Skill Creation Pipeline 重构方案

状态：已根据讨论确认基础设计，进入分阶段实施。设计目标不等于已实现能力；实际支持范围以使用说明和验收记录为准。

代码基线：`D:\study\chem-agent-toolkit`，commit `6bb535a`。
本文结合两版现有 pipeline、最小内容约束、封装规则，以及 BioNeMo Agent Toolkit
和 AtomisticSkills 的案例，提出一条统一的新构建主线。

## 1. 目标与首版边界

目标是将有依据的工具能力，构建成 Agent 能正确选择、调用和检查结果的 skill。
最小产物可以只有一个 `SKILL.md`；任务确有需要时才增加参考文件、脚本和小型资源。

首版完成一个明确任务从资源输入到可检查产物的全过程。优先保证少量产物实际可用，
不以生成数量、文件数量或引用数量衡量成功。

首版支持：

- 包装已有 Python API、CLI、HTTP 服务或已配置的远程执行入口。
- 为已有论文实现整理轻量调用入口，保持原有算法行为。
- 基于明确方法依据，为工具增加有限的检查、后处理或诊断能力。
- 模型直接编写最终文件；程序检查、组织测试、反馈问题和组装产物。
- 生成精简构建记录，并清理成功构建中的可再生临时内容。

首版不承担：从论文公式重新实现完整算法、自动训练模型、自动搭建大型环境或集群、
自动建设 MCP 服务、大规模无目标能力挖掘、跨论文语义合并、复杂 workflow 编排。
这些属于明确的后续扩展，不进入基础成功路径。

用户已有环境与运行配置应尽量复用。下载大权重、部署服务、付费远程任务等不因为
生成了说明文字就自动执行；缺少实际运行条件时如实保留草稿及缺口。

## 2. 已形成的设计决定

1. 最终文件由模型编写，不再通过固定章节渲染器拼接。
2. 强制的是四项最低信息覆盖，不是固定标题或章节顺序。
3. 简单工具包装是正式产出，不再只作为 `atomic_resource_hints_only` 的附属结果。
4. 来源审计、运行证据与 Agent 使用材料分开管理。
5. 以一个可独立验收的任务确定粒度，不按整个软件包或每个 API 机械切分。
6. 工具接口形式与 skill 大小分开判断；复杂模型不必对应复杂说明。
7. 能调用、结果符合接口约定、科学结论有依据、Agent 使用有效，是不同层次的证据。
8. 一条正式代码主线；不继续长期维护两套近似 pipeline。
9. 构建与安装、发布、Git 提交分离。完成构建不自动更新正式目录或推送。
10. 每增加一个文件、模型调用或检查步骤，都应有具体用途。

## 3. 一次构建处理什么

先明确两个维度：

| 维度 | 取值 | 决定什么 |
| --- | --- | --- |
| 封装目的 | 直接包装 / 特殊用法或能力扩展 | 是否需要新增方法、假设和判定依据 |
| 工具就绪程度 | 已有入口 / 需轻量适配 / 缺关键实现或资源 | 能直接写 skill，还是先整理入口或报告缺口 |

随后按实际需要选择单文件或扩展文件组织。复杂度判断不要求出现在最终正文中。

格式校验、非空检查、返回状态检查、结果保存属于正常调用契约。
新增科学判据、诊断计算或新的接受/拒绝策略需要声明为扩展。
扩展使用现成验证库时，可以是工具直接包装；是否称为扩展取决于相对既定任务
新增了什么，不以是否自己写了算法判断。

合并或拆分规则：

- 必要输入准备、实际执行、结果读取可以保留在一个 skill 内。
- 同一任务的本地/托管模式通常以分支与参考文件表达。
- 目标、输入输出或成功判据不同，且可独立使用时，考虑拆分。
- 不为压缩行数强拆，也不因调用同一个库就把不同任务全部合并。
- 首版一次构建一个任务。只有资源输入时可先输出候选任务供选择，不直接批量构建。

## 4. 基础工作流

```text
接收任务与资源
  → 按需阅读并核对实际入口
  → 形成简短封装方案
  → 必要时整理适配/扩展代码
  → 建立一个最小可检查实例
  → 模型编写 skill 文件
  → 检查、有限修正、重新检查
  → 输出包和必要记录
  → 成功清理临时材料
```

示例与写作可以迭代。一个非常简单的工具可先写最小调用再运行；复杂适配应先
确认入口。最终交付前必须用实际检查结果校准说明，不能把预期结果写成实测结果。

### 4.1 接收任务与资源

用户提供任务描述，以及文档、仓库、论文、服务说明或小型输入数据。无需每次提供论文，
也不要求用户填写完整内部契约。

程序记录来源位置和可获得的版本信息；远端来源只抓取相关内容，代码优先固定 commit，
已安装工具记录版本。论文支持方法论，API/源码/schema 支持实际调用约定，不能相互替代。
复制或改写上游代码时记录来源与许可要求；获取资料不自动意味着可以重新分发。
许可未明确的实现不能因为生成成功就标成可公开发布，文档引用与代码分发分开处理。

### 4.2 阅读与能力分析

模型能够按需查看入口、参数定义、返回结构、示例和依赖文件；不继续强制只读自动按文件名
选出的少量片段。资料过多时先检索定位，再读取相关部分，避免整库注入。

需要回答：任务边界是什么，入口是否真实，所需资源是否可用，哪些规则有依据，哪些未知。
程序提供来源索引和事实记录，不代替模型推断科学含义。

### 4.3 形成简短封装方案

方案是后续构建和检查的依据，不是最终正文的固定字段表。最少记录：

| 内容 | 用途 |
| --- | --- |
| 任务与边界 | 防止范围漂移、决定是否需要拆分 |
| 工具入口与依赖 | 确认能力能被调用，区分现成与待适配部分 |
| 新增行为 | 无 / 适配 / 扩展，并说明具体变化 |
| 文件计划 | 每个计划文件的作用与读取条件 |
| 检查计划 | 测试输入、预期行为、关键判定和依据 |
| 关键来源与缺口 | 支撑接口及方法事实，标明无法确定的内容 |

结构化格式只保证程序能读这些信息，不要求为所有工具填满大量空字段。
不固定每份来源必须产生几个 skill，也不强制直接包装具有科学决策分支。

### 4.4 必要的工具适配与扩展

可直接调用的接口直接复用，不统一套一层 wrapper。
必要适配可以包括路径参数化、整理已有命令、统一输出、保留原始索引等。
扩展需要写明方法、适用前提、额外输出、判定依据和缺失证据的处理。

单个 skill 私有的脚本放该 skill；多个 skill 真正共用的稳定实现才进入共享工具层。
不复制整份上游仓库进每个 skill。适配脚本不能假定复制一份推理脚本就拥有完整依赖。

若只有论文算法而无可恢复实现，标记为需要单独开发，不自动启动无边界的复现工程。

### 4.5 模型编写产物

模型在独立 staging 目录中编写 Markdown、必要代码和小型资源。程序也可以原样落盘
模型返回的文件内容，但不得用字段重新拼装正文或覆盖模型的章节组织。

写作遵守唯一的最小标准与封装规则：四项信息覆盖、按需扩展、真实调用、避免重复。
首版模型产物使用英文；构建摘要可按用户语言输出。

模型应能查看已确认入口和检查证据；不需要读取全部历史日志。写作期间不修改正式 skill、
上游源码或 pipeline 自身。新增或删除产物文件必须反映在最终文件清单中。

### 4.6 检查与有限修正

程序优先运行确定性检查，随后只对重要的内容一致性和方法边界开展针对性审阅。
首版不要求每个简单包装都再做一次昂贵的全文模型复核。

存在复杂适配、新增科学判据或明确的审阅风险时，增加内容审阅。无法机械确认的四项
最低信息覆盖由针对性内容审阅检查，不能用标题正则冒充语义检查。

把具体错误、相关文件和证据交给模型修正；每次修正后重跑受影响检查。
默认至多两轮修正，并设置可配置的时间/调用预算。相同阻塞无新证据时停止无效重试。
任务范围、算法或新增判据发生实质变化时，返回方案阶段更新记录。

### 4.7 输出与清理

输出到独立目录：技能包与一份精简构建记录。正式安装必须是单独操作。
安装采用检查过的文件清单及哈希，避免安装过程中混入未验证修改。

确认输出可读、记录完整且最终内容哈希匹配后，才清理本次成功构建的临时目录。
失败或受阻时保留足够的错误证据和可继续的工作内容，不继续堆积完整成功日志副本。

## 5. 最终 skill 的内容和文件规则

最低内容以 [../skills/minimum.md](../skills/minimum.md) 为依据；不同情况以
[../skills/packaging.md](../skills/packaging.md) 为补充依据。

```text
<skill-name>/
  SKILL.md           # 必需；简单工具可以到此为止
  references/        # 可选；参数、部署、特殊模式等按需读取
  scripts/           # 可选；确有价值的私有适配或扩展实现
  examples/          # 可选；有复用价值的小输入、调用说明与预期行为
  resources/         # 可选；运行必需的小型模板或资源
```

不生成空目录。复杂科学假设、必须检查的收敛条件等不能藏在可选读取材料中。
示例包含什么应与任务相称：一个简单查询不要求完整数据集，复杂验证应包含能区分
通过/失败的例子。实验结果大文件不随技能包默认分发。

不要求同一个例子在正文、参考文件、example README 各写一遍。指定唯一版本，其他地方链接。
每个脚本示例必须指向真实入口；必需的隐式仓库依赖必须声明，不能假装文件夹完全独立。

## 6. 检查体系与证据边界

| 层次 | 首版检查 | 不能因此声称什么 |
| --- | --- | --- |
| 文件与接口 | frontmatter、包内链接、引用入口、配置字段、路径、依赖声明 | 不证明计算正确 |
| 运行 | 最小调用、退出/任务状态、可解析输出、必要副作用与实际结果字段 | 不证明科学有效性 |
| 任务与方法 | 关键前提、单位、索引、收敛、扩展判据、结果解释 | 不证明普遍适用 |
| Agent 效果 | 独立真实任务中完成质量、成本、恢复表现 | 少量样例不证明普遍增益 |

具体规则：

- 检查实际接口，而非要求固定章节顺序或固定措辞。
- 能安全执行的 CLI 可先检查 `--help`；这不是功能用例的替代品，也不对有副作用的
  非标准入口盲目执行。HTTP/远程任务只在实际访问与执行条件具备时检查。
- 结构格式检查和方法判据应来自独立的接口/来源事实或既定需求，不能只复述待测实现。
- 简单任务至少有一个正常调用实例；有非平凡输入限制或错误语义时补边界/失败实例。
- 验证/筛选扩展至少包含通过和失败实例；缺失证据需要测试时再增加不确定实例。
- 原始字段、单位、索引对应与实际使用的默认参数要可追踪。
- 所有检查报告使用 `pass / fail / not_run / not_applicable` 并给出必要原因，避免
  空数组被解释为全部通过。预期拒绝是测试通过，不是构建失败。
- 引用检查针对关键事实、数值规则及方法判断。正文不再逐句强制行号引用；证据记录
  保存关键原文片段/定位、来源版本与相应事实。模型审阅不等同于独立科学验证。

## 7. 轻量内部记录与最终状态

原操作契约拆成“任务/构建方案”和“检查证据”，不再直接映射到正文。
内部记录只服务于调度、追踪、检查和复现；不生成另一个要模型反复读的长文档。

建议每次最终保留一个 `build.json`，包含：

- 构建 ID、工具/任务标识、时间、pipeline 与规范版本。
- 规范化输入说明、资源位置、版本与必要哈希。
- 方案摘要：任务边界、适配/扩展、文件选择及关键依据。
- 最终文件清单与内容哈希、依赖/外部资源及获取条件。
- 检查摘要、相关小型用例定位、失败原因及尚未解决项。
- 模型标识、可获得的 token/调用数/耗时；缺失值记未知，不记零。
- 如使用重放，记录重放事实；重放不算新的独立抽取或效果证据。

不在这个文件保存密钥、认证头、完整环境变量、完整提示词或每轮全文响应。
实际运行的科研参数可写入任务输出的运行清单，不必嵌进 skill 正文或复制进每份报告。

包状态建议为：

| 状态 | 含义 |
| --- | --- |
| `ready` | 本次适用的必需检查通过，声明任务已获得最低执行证据；不等于 Agent 增益已证明 |
| `draft` | 有明确入口及可读产物，但仍有必需运行或内容检查未完成 |
| `blocked` | 缺少入口、资源、权限或方法信息，当前无法继续声明任务 |
| `failed` | 构建或必需检查失败，有限修正后仍未解决 |

各层证据另列，不用一个状态替代全部结论。`ready` 必须限定已测试模式和范围，不能以
一个 CPU 小例子宣称 GPU、远程和全部模型后端都已验证。

## 8. 构建材料的保留、清理与可复现性

原则：长期保留“实际交付了什么、依据什么、检查了什么、怎样重现关键行为”。
避免长期保留可重新生成的多份过程副本。空间管理与复现要求发生冲突时，应明确报告
可复现范围，不能一面清除唯一证据，一面声称完全可重放。

| 材料 | 默认处理 |
| --- | --- |
| 最终技能包及必要私有脚本 | 保留 |
| 每次被正式采用版本的精简 `build.json` | 保留，关联 skill 与代码版本 |
| 小型回归用例、必要输入与期望行为 | 保留唯一版本，正式测试不与生成提示词混用 |
| 关键来源定位和支撑接口/判据的必要片段 | 保留在构建记录或引用的精简证据文件中 |
| 完整论文、源码检出、依赖和模型权重 | 按版本/内容共享缓存；受许可与体积约束，不每次复制 |
| `messages.json`、完整 prompt、逐轮响应、重复 bundle、临时渲染目录 | 成功收尾后默认清理；调试选项才保留 |
| 失败构建的有效工作文件、最后错误、复现输入 | 保留精简失败包；以后可显式清理 |
| 大型轨迹、下载中间件、临时计算文件 | 只保留任务必需结果或获取方式，其余按本次工作区规则清理 |
| 正式 Agent 实验原始回答、工具轨迹、判分与成本记录 | 在独立实验目录保留；不按普通构建临时日志删除 |

补充约定：

- 可选 `keep-debug` 保留详细调试材料；说明可能包含用户输入，且不默认进入 Git。
- 写入错误摘要或保留日志片段前处理可能回显的密钥与认证内容，调试模式也不保留凭据。
- 只依靠可变 URL 与文件哈希无法保证原文可恢复。关键事实保留必要片段；完整逐字重放
  需要可保留的来源快照和响应，显式选择调试/归档模式时提供，不作为默认声称。
- 依赖版本和权重哈希记录实际已知值；不可访问的资源不编造校验和或下载成功记录。
- 不仅靠 `.gitignore`：已跟踪文件不会因此消失。历史迁移需逐项核对后决定保留位置。
- 自动清理只覆盖 pipeline 自己创建且登记的工作区，核对绝对路径，不跟随链接删除来源。
  不清理用户输入、手工修改、正式技能、失败证据和正式实验记录。
- 首版提供按 run 的显式清理与成功临时清理，不加入复杂定时清理策略。
  共享缓存采用显式清理，显示可能影响的历史复现，不与本次构建结束一起随意删除。

## 9. 建议的项目组织

```text
creation_pipeline/                 # 唯一正式实现
  __main__.py                     # 统一入口
  cli.py                          # 命令参数
  pipeline.py                     # 可读的阶段编排
  models.py                       # 小型内部记录与状态定义
  intake.py                       # 来源读取、索引、共享缓存
  analyze.py                      # 能力分析与封装方案
  author.py                       # 文件编写、局部修正
  checks.py                       # 接口/内容检查调度
  runtime.py                      # 最小实例执行与结果采集
  package.py                      # 文件清单、输出、安装分离
  records.py                      # 构建摘要与受控清理
  model_backend.py                # 一种首版模型执行后端
  prompts/                        # 少量阶段指令，引用规范而非复制整套规范

tests/pipeline/                   # pipeline 自身的确定性测试与小型 fixture
evaluation/                      # Agent 效果实验，独立于构建验收
skills/<skill-name>/              # 新增正式 skill 的单一权威位置
tooling/<tool-id>/                # 只有跨 skill 共用的适配实现才建立
build-records/<skill-name>/       # 被采用版本的必要构建记录
docs/
  README.md                      # 文档索引
  skills/minimum.md              # 最小要求的唯一权威文本
  skills/packaging.md             # 粒度、条件扩展、文件职责
  pipeline/design.md             # 工作流、模块职责、状态、保留规则
  pipeline/usage.md              # 用户运行方式、最小配置、排错

.pipeline/                       # 本地工作材料，默认不进 Git
  cache/                         # 按版本/内容标识的共享来源缓存
  runs/<build-id>/               # staging 与临时检查材料
  outputs/<build-id>/            # 构建完成的包 + build.json
  failures/<build-id>/           # 精简失败证据与可继续内容
```

上面是模块职责，不要求为了凑齐文件先拆出大量空模块。实现时可合并很小的模块，
保持单向、显式调用，避免首版引入插件框架或多后端路由系统。

新 skill 优先使用一个权威路径，分类用元数据或目录索引表达，不再自动多处复制。
现有分类目录和安装入口首版暂不全量迁移；逐项确定权威来源后再迁移或建立明确链接。
现有科研工具和模型包不因重构 creation pipeline 自动改写。

## 10. 文档管理与可读性

每份文档只负责一个问题：最小要求、封装规则、pipeline 设计、使用说明。
主 README 简短介绍项目并链接这些文档，不重复列出全部规则和历史实验。

规范、提示词、校验器之间建立职责分工：规范定义原则，提示词指向该原则并说明本阶段
动作，校验器落实可检查部分。不得维护三份独立且稍有差异的完整标准。

旧设计和负结果不抹除，但不全部堆在当前操作指南中。必要历史记录由简短索引指向
Git 版本或归档位置。运行文档明确区分“已实现”“需手动”“未验证”，不把计划写成能力。

本工作目录当前的最小要求与封装规则，在实施时迁入上述权威位置；旧路径以短链接说明
代替全文副本。本提案确认后归入 `docs/pipeline/design.md`，不另立一套相互重复的设计书。

## 11. 建议的首版使用方式

以下为拟议接口，不是当前可执行命令：

```text
python -m creation_pipeline plan <build-config>
python -m creation_pipeline build <build-config>
python -m creation_pipeline check <package-or-build>
python -m creation_pipeline install <checked-output> --destination <path>
python -m creation_pipeline clean <build-id> --dry-run
```

`plan` 可能调用模型读取并分析，不能与无模型调用的静态预检混淆。
需要静态预检时用明确选项表示。`build` 一次完成主线，默认不安装、不 Git 提交、不推送。
受阻时输出缺口而不是不停尝试。手工修改后的包再次检查，原记录不自动代表新内容。

最小配置只需要任务与来源，其他采用有明确含义的默认值，例如：

```yaml
task: Package the tool's molecular similarity calculation for agent use.
sources:
  - path: ./tool-repository
    ref: <resolved-commit-or-user-selected-ref>
  - path: ./tool-documentation.md
```

环境、测试输入、扩展目标等按需加入。模型可以提出补充信息需求；已能从资源中核实的
事实不反复向用户询问。缺少决定任务范围或科学判据的信息时才停在对应阶段。

首版使用现有本地模型调用途径，改造成支持必要阅读和 staging 写作的执行后端。
不同时实现多个提供商、并发子 Agent 或自动选模型；记录实际使用后端与成本即可。

## 12. 旧代码如何处理

| 现有部分 | 处理方向 |
| --- | --- |
| 文档解析、来源哈希、固定 Git 版本读取 | 提取可用部分，合并为来源模块 |
| 固定选文件、上下文截断 | 保留覆盖记录，改为检索与按需阅读，不能默认代表整库阅读 |
| v1/v2/v3 多套候选 schema | 新建轻量构建记录；旧格式只在独立兼容读取中处理 |
| 操作契约 | 保留有价值的信息原则，取消与正文固定映射；适配不同包装任务 |
| `codex_extract.py` 和禁止工具的模型调用封装 | 改为阶段化分析/写作后端，允许受控读取与 staging 写入 |
| `render_drafts_v03.py` | 不进入新生成主线；历史重放从旧版本读取 |
| `validate_skill_format.py` | 改为最小内容、文件及接口检查，不以固定七章节验收 |
| 资源恢复清单、文件存在性和哈希核对 | 吸收进资源记录与打包，不强制每个 skill 展示长清单 |
| `validate_tool_execution.py` | 复用有价值的 fixture 执行逻辑，区分 CLI/API 等运行形式 |
| 自动分类镜像、构建时提交推送 | 从核心构建移除，安装/发布独立 |
| 大批采集、自动抽象去重 | 移出首版核心，后续基于稳定接口逐个加入 |
| 已有 A/B、三臂评测与负结果 | 保留独立历史与可用统计代码，补真实工具任务评测 |

迁移先固定旧版本并清点有效结果，再建立新主线。不要一次搬迁全部资源、技能和历史日志。
旧两个实现最终通过 Git 版本与一份 legacy 索引保留，不在主工作树继续维护两套完整副本。
必要旧命令可短期提供明确的弃用提示，不把兼容逻辑塞入所有新模块。

## 13. Agent 效果评估（独立后续工作）

Agent 增益评测不进入基础 pipeline，不在每次构建后自动运行。pipeline 大调整并产出一批有价值的 skill 后，再独立设计 benchmark、多组平行对照与统计分析。构建模型可以辅助提出测试候选，但不得同时作为出题、标准答案和最终判分的唯一来源。

基础构建仅运行文件、接口、执行和必要结果检查。模型可以提出工程检查，预期值优先来自官方示例、已有测试或独立规则；这些检查不代表 Agent 增益或全面科学验证。

比较无 skill、精简 skill、扩展 skill 时，底层工具、版本、权限和输入保持相同。
如果 skill 新增了脚本，必须明确测量的是“整个包的帮助”还是“文字指导的帮助”。
测量文字收益时对照组也能访问同一工具实现；测量新增工具收益时另设基线，不能把
给工具与给说明的变化混成一项效果。

任务应覆盖正常使用、邻近但不适用情形，以及相关失败恢复。独立冻结预期结果；
不能只把模型刚生成的例子作为自身效果证明。真实运行指标包括完成质量、正确恢复、
输入/输出 token、工具调用、重试、耗时和可获取的费用。

参考文件按需读取，不在 with-skill 条件下无条件注入所有文件。保留正式实验原始记录。
小样本结果限定在所测范围；没有优势时优先查任务难度、接口设计、冗余说明与错误引导，
不通过事后改答案或只报告有利任务解决。

## 14. 实施顺序与验收

### 阶段 A：确认设计并冻结旧基线

在独立分支 `pipeline/task-skill-v1` 实施，不在 `main` 修改或向其推送。普通分支继承基线文件；不相关的历史 skill、旧实现和生成产物可在新分支中整理移除，原主分支和 Git 历史保留。

确认规范职责，记录旧基线和必要历史结果。验收资源优先使用已有工具、已收集资料和用户指定任务；不足时再搜索补充，登记论文公开来源、对应代码版本、许可、环境成本和可核对结果。论文不是必需输入，不从仅有公式且无实现的论文开始。

### 阶段 B：建立直接包装闭环

实现统一入口、来源登记与按需读取、简短方案、模型写文件、检查反馈、输出及清理。
先用一个已有入口的轻量工具跑通，验证单 `SKILL.md` 可以合法通过。

### 阶段 C：补适配与扩展路径

加入已有论文代码的轻量适配，以及一个有明确依据的验证/后处理能力。验证私有脚本、
必要示例和按需参考文件的组织。范围超出轻量适配的项目明确受阻，不假装完成。

### 阶段 D：整理、对照与迁移

使用不同于开发调试材料的新资源开展独立端到端验收；根据问题压缩说明和修正规则。Agent 集中对照另行开展，不阻塞基础版交付。统一文档入口，移除主工作树
重复实现与可再生历史副本。历史保留与删除在清单中明确，逐项迁移，不自动全库清空。

首版验收应至少满足：

1. 三类任务分别跑通：已有工具直接包装、已有实现适配、来源支持的能力扩展。
2. 简单任务允许只有主文件；复杂任务增加的每个文件能解释其用途。
3. 最终正文确由模型编写，程序未重新渲染成固定章节。
4. 文档入口与实际代码一致；适用的最小运行与结果检查通过。
5. 一个验证扩展能区分通过/失败，并明确证据不足的处理（如该任务存在此情况）。
6. 缺资源、错误接口或修正失败时有明确状态；不会报告虚构的成功。
7. 交付包、构建记录和内容哈希关联正确；没有凭据或无用过程副本混入。
8. 成功清理不会删除来源、最终输出或用户文件；失败记录足以定位关键问题。
9. 构建不自动安装、分类复制、提交或推送；手工修改能使旧验证记录失效或要求复检。
10. 新代码有针对实际风险的测试，文档能让维护者理解入口、阶段、状态与输出位置。

基础版不要求完成 Agent 对照。先用可控样例检验流程，再使用简单工具、复杂包装、论文实现适配/来源支持的扩展等真实资源端到端验收；开发案例与新资源验收案例分开。未实际完成的案例如实标为待验证，不以重放模型响应替代新模型构建。

## 15. 本轮提案的重点取舍

- 用一个任务构建闭环替代一开始的大规模自动挖掘。
- 给模型文件组织自由，同时保留真实接口与方法边界约束。
- 对简单调用减少写作与复核成本；对新增能力加强实现和判据检查。
- 保留必要证据，但不默认保留所有提示词、每轮响应、来源副本和调试轨迹。
- 不为未来 MCP 提前搭完整服务框架，先定义可复用的调用与结果约定。
- 不把整个项目一次重排；优先统一 pipeline，其余目录有计划地逐步迁移。

本方案已获准按阶段 A—D 实施；实现进度、限制与实际验收结果单独记录，不把设计目标当成实测结果。
