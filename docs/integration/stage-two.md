## 已实现

- 在 partner 主流程的内容审阅之后接入运行需求、绑定、规划、冻结及构建；
  草稿和有依据无需执行的候选保留原路径，需求不明/绑定不明保存具体阻塞。
- 自动绑定只接受唯一的交付文件与注册来源字节对应关系；支持带来源引文的显式绑定。
- 从旧 runtime 提取 inventory、按需读取、结构化模型计划/补丁、来源断言与测试覆盖校验。
  不迁移旧 lifecycle、CLI、七章节模板或独立发布逻辑。
- 生产默认取消旧总时长、尝试、读取、文件数/大小配额；保留显式限制和操作超时。
  重复诊断或无新增材料的读取停止。正常流程共享全局/候选模型预算。
- 检查 Docker 引擎平台、CPU、内存，以及当前范围必需的资源。
  模型的 `available` 声明不作为主机事实；缺失、未知、尚无支持的条件分别保留缺口。
- 生成 Dockerfile、实际交付入口、源文件、锁定测试和规划证据；软件安装只在 Docker build 内发生。
- 本地 build 回执绑定全部输入指纹，记录真正的镜像 ID、标签、平台、日志与交付文件核对。
  构建后通过未启动容器的文件复制核对镜像内源码，不执行任何业务测试。
- 动态构建尝试独立存储并校验，通过现有 catalog 事务持久化；保留历史。
  `built` 对应 `execution_status=not_run`，不晋升正式区。
- `runtime-build` 从冻结候选恢复构建；`runtime-prepare` 建立环境新修订，保留来源、
  交付字节和已有锁定测试，不重新发现或编写 Skill。
- 保留绑定的执行请求/回执接口。远程 target 被本地实现明确拒绝；没有远程服务。

完整目录、数据协议和配置见 [Docker build protocol](../pipeline/docker-build.md)。

## 实际验证

环境：Windows 宿主，Python 3.14.3，已存在的 jsonschema 4.26.0；
Docker Desktop 4.95.0 / Engine 29.8.2，Linux amd64，12 CPU，约 8.1 GB 引擎内存。
沙箱最初不能访问 Docker 管道；按授权访问宿主后确认服务可用。没有为本任务安装宿主依赖。

1. 修改前阶段一回归：125 项通过。
2. 阶段二新增机制测试覆盖需求/绑定未知、Docker 不可用不调用模型、必需/可选资源、
   计划与构建输入变化、锁定断言、明确预算、重复读取停止、持久化与恢复。
   全量回归 140 项通过，最终 runtime 接口复验 17 项通过（含随后新增的 2 项绕过/镜像丢失检查）。
   结果见 [tests.log](../../validation/stage2/tests.log) 和
   [runtime-tests.log](../../validation/stage2/runtime-tests.log)。这些测试中的模型/Docker
   doubles 只验证程序机制，不作为真实执行证据。
3. 真实 planner 两次调用：首次计划被“行为测试缺少断言”校验拒绝，保留原响应和回执；
   第二次使用真实模型补丁修正，原校验未放宽，测试未执行，未根据运行输出改期望。
4. 固定来源 RDKit 样例：脚本、requirements 和参考材料从 `d5b77dc` 逐字节提取，
   镜像安装 `rdkit==2024.9.6`、`numpy==1.26.4`、`pillow==11.3.0`。
   最终接口真实构建成功，镜像 ID：
   `sha256:1c10de11b64ef5e32b7d29331d1d765d5d24931f9f1832b19745a44c673486b6`。
   持久化后的镜像和文件完整性再次通过只读核对。
5. 受控负例在相同计划最后增加明确标注的 `RUN exit 37`，真实 Docker build 失败，
   记录 `build_failed`，而不是 `runtime_blocked` 或业务执行失败；没有修改交付源码/测试。
6. 两个真实构建探针都留在候选区，默认查询为空，资格为 false。
   探针的内容审查是 `not_reviewed`、业务验收是 `not_run`；没有伪造作者或独立审阅结果。
   新主流程接线由机制测试覆盖，此处的真实模型验证范围是 runtime planner。

持久化证据入口：[verification.json](../../validation/stage2/verification.json)、
[成功候选库](../../validation/stage2/rdkit-library/catalog.json)、
[失败候选库](../../validation/stage2/build-failure-library/catalog.json)、

首次预检曾错误地把计划中的“尚未执行”和 SMILES 验收局限也当作资源未知。
已将资源判定固定在显式 `resource_assessment` 和必需资源列表；一般科学/测试局限
继续保留并交给后续验收，而不作为无法开始构建的理由。锁定断言未因此改变。

## 明确未完成及下一阶段接口

阶段二只证明材料可准备、镜像可构建、交付文件未被构建步骤篡改。
没有业务执行验收、GPU 执行、远程服务、外部服务连通性验证或正式区晋升。
当前实现为单交付文件入口；无明确交付入口的纯指令型可执行 Skill 会阻塞并要求建立绑定。
GPU、私有依赖、服务/运行网络等缺少本地核验能力时保守保留 `runtime_blocked`。
没有自动模型修复 Docker build 失败；支持显式环境修订后重建。

样例计划仍明确记录 SMILES 完整有效性不能仅用正则断言、数值科学正确性未独立证明等局限。
这不影响阶段二镜像构建事实，但不能被阶段三忽略或转成业务通过。
基础镜像计划使用公开标签，实际构建日志保留解析身份；重建可能产生新镜像，
后续验收必须绑定本次真实 ID，不能将旧标签或历史构建事实当作新验收。

阶段三应消费 `RuntimeRequest`、冻结 `runtime/locked-tests.json` 和不可变镜像 ID，
实现真实交付入口运行、业务断言、资源挂载/容器限制、证据核验及正式资格判断。
发现内容缺陷时撤销内容通过并重新独立审阅。镜像丢失/资源变化通过当前核验单独表达，
不得改写历史事实。后续可扩展同样绑定字段的授权远程执行，但这里没有实现或验证它。
