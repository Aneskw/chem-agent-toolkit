# Planner 超时：调试与归因方案

基于你 10/27 的合并核对（真实 planner 运行 13 例、本地机制测试 12 组），以及本轮 batch-3/batch-4 的新证据。**当前最能站住的判断**：主要故障在 CLI 与后端之间的**响应流／路由链路**；本地监督与错误分类缺陷让部分故障被误判或拖满 600 秒；尚不能唯一定位到代理／网络／服务端／CLI 解码。

本方案的目的不是再跑一次，而是把**决定性的三个不可观测点**变成可观测，并用一张决策树把“下一步该做什么”定死。

## 1. 事实分层（不要混算）

| 层 | 已复现的事实 | 归因强度 |
| --- | --- | --- |
| L1 链路/路由 | `workspace routing discovery timed out`（10/26 22:47，doctor 同时报不可达）；`peer closed connection without TLS close_notify`；握手 EOF | 强：该轮直接原因明确 |
| L2 响应流 | `stream disconnected before completion: Transport error: network error: error decoding response body`，batch-3 连续 4 次、batch-2 一次 | 强：当前最直接的传输异常证据；**但只能到“响应体/流层面”** |
| L3 超时表现 | 600 秒硬上限；batch-3 静默 365s、batch-4 静默 593s；CLI 自带重试 1–5 全部出现 | 中：说明“为什么能拖到 600 秒”，不解释“为什么没有数据” |
| L4 本地误判/盲点 | 可恢复重连被判终止（已修）；计数为 0 与 `plan_unresolved` 误分类（已修）；WS idle 盲点（本地证明） | 确定缺陷，但只解释“误判与延迟”，不解释远端无响应 |
| L5 计划/内容问题 | `Outcome assertion role must match…`、引文拼接、入口歧义、schema 污染 | 确定缺陷；与 600 秒等待不同类 |

归因边界：L1/L2 都可能由**本机代理/TUN、中间网络、后端、CLI 解码实现**任一处产生，现有证据无法区分。

## 2. 三个决定性缺口与获取方式

### 缺口 A：服务端接收/完成状态与可查询的 request/response ID

这是唯一能一刀切开“链路 vs 服务端 vs 客户端”的证据。我们至今没有它。

- **保存方式（修正）**：仅对**白名单、非认证性质**的 `request_id` / `response_id`，把**原值**保存在受限本地证据目录（不进报告、不进 catalog、不进常规日志）；报告与汇总只显示 SHA-256。若某 ID 取不到原值、只能取哈希，**必须先确认维护方能按同一算法关联**，否则该 ID 对 A2 无效。
- **三类 ID 不可互替**：本地 `thread_id`（CLI 会话）、网关 `request_id`（一次 HTTP/WS 请求）、`response_id`（Responses API 响应）。交付给维护方时必须标明是哪一类、取自哪条日志行。
- **A1（本地，0 模型调用）**：提高日志级别**不保证** CLI 输出这些 ID，因此 A1 的成功判据不是“投影器能解析手写字符串”，而是：在固定版本上，用**本机合成服务**跑通一次真实 CLI 调用，并在真实 stderr 中**实际出现**可提取的 ID 字段。取不到就如实记为“该版本不具备”，A2 改为只交时间窗 + thread_id。
- **A2（外部）**：把白名单 ID 原值（或经其确认的哈希）+ UTC 时间窗 + thread_id 交给维护方，确认该请求是否到达、是否创建响应、是否发出业务事件。


### 缺口 B：失败前的流事件分类（不是字节数）

现在只有“有没有 ERROR 文本”，没有“流在什么状态下怎么断的”。

- **B1（本地，真实 CLI，不碰真实请求）**：自建**可控 TLS 端点**（自签 CA 注入子进程环境，不是 MITM 线上流量），用真实 `codex exec` 打合成场景：
  1. 正常完整 SSE 响应；
  2. 发送头部后静默；
  3. 中途截断连接；
  4. 发送不完整 chunk / 错误 Content-Length；
  5. 伪造 `response.completed` 后立即断开；
  6. 慢速分块。
  每场景记录：CLI 的错误文本、重试次数、是否重发、最终退出码。
- **产出**：`错误文本 → 触发条件` 映射表。它只证明“在已测试场景中，X 能复现这条错误”，**不能**证明线上只能由 X 造成；因此归因只能写“与 X 相容”，不能写“即 X”。
- **必须分开的场景维度**（否则无法判断 CLI 优先接受业务完成还是要求底层消息体完整）：
  1. HTTP 消息完整性：完整 Content-Length / 不完整 body / 错误 chunk framing；
  2. 内容编码：正常 / 损坏压缩体；
  3. SSE/JSON 协议：完整 / 非法 JSON / 缺少 `response.completed` / 非法 kind；
  4. 连接关闭：正常关闭 / TCP reset / TLS 非正常关闭（后者需 TLS 端点）；
  5. “发送合法 completed 后正常结束” 与 “发送 completed 后截断 HTTP 消息体” **分别作为独立场景**。
- **安全边界（硬约束）**：端点只绑定 `127.0.0.1`；使用合成输入与无凭据环境（独立临时 `CODEX_HOME`，不继承认证）；若需 TLS，CA 仅通过子进程环境注入、**保留证书校验、不写系统信任库**。零模型调用不等于零操作成本或自动获得全部权限。


### 缺口 C：把“进程 I/O 计数”从进度判据里剔除

`GetProcessIoCounters` 是进程级累计值，含文件 I/O，不能证明网络持续收包，更不能证明生成进度。当前代码用 `inbound_activity_seen` 参与“是否停滞”的判断，这会让一个频繁读写文件的子进程掩盖真正的停滞。

- **C1（P0，需你点头）**：字段改名 `process_io_growth_seen`，**不再参与停滞判定**，只作旁证入库；停滞判定回到“stdout 生命周期事件”这一单一信号。
- **C2（可选）**：若确需“是否仍在收包”，改用 socket 层计量（本地 TCP 中继按连接计字节，或 `GetPerTcpConnectionEStats`），并重新标定，不能沿用现在的结论。
- **同时修正**：`last_terminal_event_type=error` 不等于终止错误——`Reconnecting...` 是重连提示。投影时就用 `is_recoverable_notice` 分类，字段拆成 `terminal_event` / `notices_count`。

## 3. 归因决策树（每次失败按此四级分流）

```
失败发生
├─ 连接/路由阶段失败？
│   ├─ 有 workspace routing / TLS close_notify / handshake EOF  → L1 链路
│   │     动作：网络侧 A/B（TUN on/off、换代理节点、直连 vs 代理、换时段），
│   │           每次同步记录 codex doctor 两项结果
│   └─ 无上述特征但 doctor 报不可达                            → L1 链路（先修环境，不消耗调用）
├─ 流已建立、进入等待？
│   ├─ 有 error decoding response body / 流中断文本             → L2 响应流
│   │     动作：B1 合成矩阵 + A2 request_id 关联
│   ├─ 完全静默、无任何 event，直到 600s                        → L2/L3（同形：batch-4）
│   │     动作：先 A1 抓 request_id；无 ID 则优先怀疑未建立有效流
│   └─ 客户端收到完整流但报错                                   → L5 客户端解码/协议
│         动作：CLI 版本/feature 对照 + 响应体完整性校验
└─ 本地监督器自身判错？                                          → L4
      动作：离线回放该轮 events.jsonl（batch-2 已有先例），修分类并加回归
```

**关键纪律**：同一轮里若既有本地误判又有远端异常，只记录为“远端异常 + 本地误判”，**不得把本地缺陷算作超时原因，也不得把远端异常算作本地 bug**。

## 4. 排期（成本与授权）

| 优先级 | 事项 | 成本 | 需要授权 |
| --- | --- | --- | --- |
| P0 | 进程 I/O 退出停滞判定，只作活动旁证；时间线拆成五类（见 §5）；字段与报告措辞更正 | 0 | 已获准 |
| P1 | B 的合成端点矩阵（回环 HTTP，必要时再加 TLS）+ A1 的 ID 可取性验证 | 0 模型调用 | 已获准 |
| P2 | **一个已保存的固定 planner 请求，最多一次应用层启动**，固定 prompt/schema/CLI/配置指纹；不重跑发现/作者/审阅；CLI 内部重试另记，不承诺等于一次后端请求 | 1 次应用层启动 | 需单独批准；若确需多次，逐次说明用途并另行审批 |
| P3 | 把白名单 ID 原值（或经确认的哈希）+ 时间窗交维护方 | 0 | 需明确渠道与发送内容后批准 |
| P4 | 网络侧 A/B（同输入，仅链路变量） | 各 1 次启动 | 是，逐批 |

顺序：**P0 → P1 → （P1 证据）→ P2 → P3**；P4 仅在 P3 判定为链路或无回应时做。

## 5. 时间线与字段规范（强制）

每次模型调用必须分开记录五类时间，不得混为一个“进度”：

| 时间 | 定义 | 用途 |
| --- | --- | --- |
| CLI 活动 | 任何新输出行（含提示、日志） | 只证明进程活着 |
| 重试/通知 | `Reconnecting...`、回退提示 | 只证明 CLI 在自救，不是答案进度 |
| 生成进度 | stdout 生命周期事件（thread/turn/item） | **唯一**的本地进度信号 |
| 终止 | `turn.completed` / `turn.failed` / 真终止错误（`is_recoverable_notice` 为假） | 判定结果 |
| 退出 | 进程退出码与时间 | 判定完整 I/O |

`进程 I/O 增长` 仅作旁证入库（字段名 `process_io_growth_seen`），**不参与任何判定**。
静默超限只能表述为“超过本地进度窗口”，**不能**判“模型已卡死”。首批保持 `observe`，校准后再决定是否终止；**不把该规则推广到允许长工具执行的 NativeSession**。


## 5. 每次运行的记录规范（强制）

一条 run record 至少包含：`transport`（逐阶段实测）、`phase timeline`（首个 event / 首个 terminal / 静默峰值）、`error_class`（链路/流/客户端/本地误判）、`retries`（次数与间隔）、`request_id_sha256`（若取得）、`wall_seconds`、`classification` 五取一（link / stream / client / harness / unknown）、以及“本地误判是否存在”。

**分类五取一，不许写 partial 了事**；预算耗尽要写 `budget_exhausted` 并附原因，不能与其他归类混用。

## 6. 停止宣称清单

- 不能说 WS idle 缺陷是统一根因（HTTPS 同样失败）；
- 不能用 `read_bytes` 增长证明“对端仍在推流”或“模型在生成”；
- 不能把 `last_terminal_event_type=error` 当作终止失败；
- 不能说“已定位根因”，只能说到“响应流异常 + 本地盲点已复现”；
- 不能把本地故障注入、权限探针、启动失败算进 planner 超时统计；
- 不同批次的测试数量不能相加当稳定性样本。

## 7. 归因判据（降级后的版本）

| 取得的事实 | 可以判断 | 仍不能判断 |
| --- | --- | --- |
| 维护方没找到记录 | 暂未关联成功 | 请求一定未到达 |
| 已接收但未完成 | 服务端处理未完成 | 一定是服务端故障 |
| 服务端已完成、客户端报错 | 故障可能在完成后的交付/消费路径 | 一定是客户端解码 |
| 离线回放发现误判 | 本地监督器存在缺陷 | 原运行没有远端异常 |
| 合成矩阵中截断能复现同文本 | 与“响应体提前结束”相容 | 线上只能由截断造成 |

- 只有维护方确认**记录覆盖完整、ID 对应准确**时，“未收到”才有较强归因意义。
- TLS `close_notify` 缺失可发生在连接建立之后，**不能**一律归入“连接阶段失败”。
- 客户端解码问题单列一层，不并入原来的“计划/内容”层。

## 8. 已更正的对照结论（batch-3 vs batch-4）

原始 `request.json`：prompt 44,718 vs 44,990 字节，SHA-256 前缀 `29ba63ba…` vs `177ac5fd…`——**两份 prompt 不同**，因此不是严格单变量对照；`default` 也不证明实际协商为 WebSocket。

正确表述：**“在 https 与 default 两种配置下都观察到超时”**；不能写“停滞与传输选择无关”，也不能写“已证明稳定复现”。

## 9. 何时可以下结论

满足任一条才可收窄归因：

1. 维护方确认记录覆盖完整且确认未收到 → 归 L1；
2. 合成矩阵覆盖 HTTP 完整性/编码/协议/关闭四维后仍与该文本唯一相容，且远端不可见 → 归 L2（服务端/中间层仍需 A2 区分）；
3. 客户端收到完整流仍报错，且本地可复现 → 归客户端解码层；
4. 离线回放证明整轮无远端异常 → 归 L4。

在此之前，最准确的表述保持为：**响应流异常与外层超时已复现，本地存在监督盲点；唯一根因未定位。**
